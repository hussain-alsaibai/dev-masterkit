## 1. A detector that declined a file is not a file that was clean

`Bearer/bearer` is a Go SAST scanner. Its per-language implementation is selected with

```go
slices.Contains(scanner.language.EnryLanguages(), fileInfo.Language)
```

and its PHP implementation declares (`pkg/languages/php/php.go`, read from the contents API
at `?ref=main` today):

```go
func (*implementation) EnryLanguages() []string { return []string{"PHP"} }
```

`go-enry` does not classify by extension in that vocabulary. Probed on this host (go1.27.3,
`go-enry` **v2.9.6**, content `<?php echo $_GET['x']; ?>`):

| filename | `enry.GetLanguage` |
|---|---|
| `vuln.phtml` | **`HTML+PHP`** |
| `vuln.php` | `PHP` |
| `a.html` | `HTML` |
| `b.inc` | `PHP` |

So a `.phtml` file matches neither the allow-list nor a `.php` suffix check: `Scan` returns
`nil, nil, nil`, and the run **reports success**. The HTML detector already claims
`HTML+PHP`, which is why inline PHP in `.html` was scanned and only one extension was lost —
the shape of blind spot that survives for years.

**The fix is two lines** (`[]string{"PHP", "HTML+PHP"}`) plus the same guard shape in
`ProcessFile`. **Not verified here:** this tree needs cgo `tree-sitter`, and `go test` was
not run against the change — the prompt says so, and the PR must too. What *was* executed is
the classifier table above.

### Why every existing test was green

Any "the PHP detector finds this pattern" test uses a `.php` fixture. The extension that
fails is the one no fixture uses, so the suite is green by construction. The general form is
the prompt: **a detector that declines a file and reports nothing is the same failure mode as
a redaction that returns its input unchanged — the caller believes work happened.**

New: `prompts/a-detector-it-declined-is-not-a-file-it-cleaned.md`,
`tools/telling-a-decline-from-a-clean-scan.md` (the probe, the allow-list reading, and the
skipped-language counter that makes the decline visible).

## 1. `snapdb` 0.18.3 — the README import returned the module, not the function

`from snapdb import query` has been documented since v0.18.0 and **never worked**.
`snapdb/query.py` defines a function also named `query()`, and `__init__.py` did not import
it — so Python's `from package import name` falls through to the submodule and hands back the
module object. Every copy-pasted example raised `TypeError` on call. Seven patch releases
carried it because the README line was never run as a test.

Rule: **an import line in a README is a claim about the package's `__init__`, and the only
proof is executing it.** One `python -c "from snapdb import query; query(...)"` in CI would
have caught it in 0.18.0.

## 2. `tiny-event-emitter` 1.0.1 — the second module had no tests, and six defects

All 12 tests in the repo covered `tiny_event_emitter`. `event_emitter.py` — the second
implementation, shipped in 1.0.0, given a comparison row in the README — had **zero**
coverage. Writing its first tests found six dispatch defects, including `on(fn)` +
`await emit_async(...)`, which is the exact pattern in that module's own docstring, silently
doing nothing.

**31 tests added; 16 of them fail against 1.0.0.** That ratio is the point: the module was
not "mostly fine", it was half-broken in ways only a test could see.
