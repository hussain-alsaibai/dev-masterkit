# 2026-11-06 — the drift checker was right, and the sweep I ran on it was wrong

**Last verified:** 2026-11-06 (12:00 EST) — both repositories below were
re-fetched and re-swept after `git fetch`, and the published `main` of each was
downloaded as a tarball and read directly. The 2026-11-05 entry in this
directory already records the *fixes*; this entry records the one thing that
entry could not: **the sweep command that reported them still reports them
after they were fixed, because a sweep over local clones measures the clones,
not the repositories.**

## What shipped on 11-05 (already in `daily-updates/2026-11-05.md`)

`snapdb`'s `package.json` said `0.11.0` while the package shipped `0.18.0`;
`tiny-router`'s said `0.2.0` while it shipped `0.7.5`. Both guarded, or not, in
the wrong place. Both fixed on `2026-11-05T13:05Z`. Nothing below disputes that.

## What today's run found: a false negative hiding a false positive

The cron sweep ran `check_version_drift.py --root ~/github` and got:

```
DRIFT  snapdb        pyproject.toml [project]=0.15.0, package.json=0.11.0, snapdb/__init__.py=0.15.0
DRIFT  tiny-router   pyproject.toml [project]=0.1.0, package.json=0.2.0

19 repository inspected, 2 with two or more surfaces, 2 drifting,
17 with a single surface (cannot drift)
```

Read as a finding, that says two repos are drifting **today**. They are not.
Before re-fetching, the same command's supporting evidence read
`snapdb behind=0 ahead=0` — a clone reporting itself perfectly in sync while
sitting **4 commits behind** and holding `0.11.0`/`0.15.0` against a published
`0.18.0`.

| repo | clone state before `fetch` | after `fetch` | published `main` |
|---|---|---|---|
| `snapdb` | `0.11.0` / `0.15.0`, "behind 0" | behind **4** | `0.18.0` / `0.18.0` / `0.18.0` |
| `tiny-router` | `0.2.0` / `0.1.0` | behind **36**, ahead 1 | `0.7.5` / `0.7.5` |

`snapdb`'s `origin/main` ref pointed at `afcdf63` (2026-08-25) while
`git ls-remote origin main` returned `9f87c70` (2026-11-05). **The tracking ref
was stale, and every conclusion drawn from it inherited the staleness** —
including the reassuring one.

### The three failures, in the order they happened

1. **A stale remote-tracking ref reads as "in sync", not as "unknown".**
   `git rev-list --count HEAD..origin/main` answers a question about the ref,
   not about the remote, and `0` is indistinguishable from *up to date*.
2. **A checker's output inherits its input's staleness silently.** The script
   was correct — it read the files it was pointed at and found real drift in
   them. It cannot know that the tree it was pointed at is four commits old.
3. **A correct result from yesterday was re-reported as a finding today.** The
   `tiny-router` "drift" was the fix commit that had not been fetched.

## The fix is in the procedure, not the script

```bash
# sweep only what you have actually fetched, and prove the fetch happened
for d in ~/github/*/; do git -C "$d" fetch -q origin 2>/dev/null; done
python3 scripts/check_version_drift.py --root ~/github
```

`git fetch` before any fleet claim, and when a sweep reports drift, confirm the
repository's own head before reporting it:

```bash
git -C repo ls-remote origin main     # what the remote says
curl -sL codeload.github.com/<owner>/<repo>/tar.gz/refs/heads/main | \
  tar xzO --wildcards '*/package.json' | grep '"version"'
```

Both published heads proved clean from a tarball today: `tiny-router` 0.7.5 on
both surfaces (`check_version_drift.py --repo` -> `ok`, exit 0), `snapdb`
0.18.0 on all three.

Left deliberately unresolved: `tiny-router`'s local clone holds **1 commit
ahead** of `origin/main` (`404095e`, "tiny-router v0.4.0 — OpenAPI 3.1 schema
generation…"). Republishing an unpushed local commit over a published 0.7.5 is
not a judgement this sweep can make, and a force-push decision belongs to the
owner of the repository.

## The rule this adds

> **A sweep over local clones is a measurement of the clones.** `HEAD..origin/main`
> reading `0` means the tracking ref agrees with itself, not that the remote
> agrees with it. Fetch first, and when a sweep reports a defect, prove it
> against the remote before it becomes a finding.

> **A checker cannot detect that its input is stale, and it will not say so.**
> Correctness of a tool is separate from the freshness of what it is pointed at.

## The health scan: 42 red repos, 0 real

The 17:00 UTC scan reported **42 of 173 red**. Reading the runs: **41 false,
0 real**.

- The script took `run list --limit 5` and called any `failure` in that window
  "failing", without asking whether a later success existed.
  `snapdb` was green at **13:05:47** the same day and still counted red.
- `reload` was read as red on `main`; its default branch is **`master`**.
- `tiny-dist-audit` was red at 13:07 and green at 13:08:30 — it was scanned
  mid-push. A second pass a few minutes later settles it.

**"Is this repo red?" is a question about the newest run on the default
branch**, read from `defaultBranchRef.name`, not assumed.

**Second bug, same run:** `GH_TOKEN = GH_TOKEN || GitHUB_PAT || ...` — the dead
PAT shadowed the gh keyring and every call returned 401. This is the defect
`prompts/a-dead-credential-named-in-a-prompt-fails-every-run.md` already
documents for the bounty scanner, found again in a different file. Fixed:
`GitHUB_PAT` is deleted; `GH_TOKEN`/`GITHUB_TOKEN` are used only when
explicitly set, else the keyring.

`memory/heartbeat-state.json` now stores `green/yellow/red` counts and each
repo's `default_branch`, so a 139-green claim cannot absorb 42 unknown states.

## The rules this adds

> **A positive-only suite proves the code runs, not that it checks.** A guard
> that cannot be shown to reject something has not been shown to guard.

> **A scan over a time window answers "was there a failure recently", not "is
> this broken now".** The busier the subject, the more wrong it gets.

> **A credential fallback chain that always resolves is a chain that is never
> tested.** `A || DEAD_PAT || keyring` returns the token, not the working one.
