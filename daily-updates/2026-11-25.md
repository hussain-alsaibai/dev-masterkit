## 1. A wildcard origin must not carry credentials

`tiny-router` 0.9.5 (`1c64aee`).

```python
cors(allow_credentials=True)   # the one-word way to "allow cookies"
```

`allow_origins` defaulted to `["*"]`, and the middleware then **reflected the
caller's `Origin`** back with `Access-Control-Allow-Credentials: true`:

```
request   Origin: https://evil.example
reply     Access-Control-Allow-Origin: https://evil.example
          Access-Control-Allow-Credentials: true
```

That is a **valid credentialed grant**, not a refusal. Any page on the internet
could read authenticated responses from the API, provided the user's browser
held a session cookie. The simple-request path reflected too — it was not only
preflight.

**Reflecting is worse than shipping `"*"`.** `"*"` is rejected *by the browser*
on a credentialed response; a reflected origin is accepted. The "safer-looking"
behaviour was the exploitable one.

The Fetch standard forbids a `*` origin on a credentialed response, and browsers
enforce it by **withholding the response**. So even the "correct" wildcard
spelling could never have worked for the call that needed it: that configuration
only failed *safely*, because the browser — not the library — enforced the rule.
**A library that delegates an illegal combination to the browser has not
validated it**, and it fails silently.

Fix: `ValueError` at construction time when credentials are on and origins are
unset or wildcard, with the remedy in the message (`allow_origins` is named).
Four probes, all in `tools/probing-both-paths-of-a-default.md`:

| probe | result |
|---|---|
| `cors(allow_credentials=True)` | `ValueError` |
| `cors(allow_origins=["*"], allow_credentials=True)` | `ValueError` |
| own origin, credentials on | grant echoed, `Allow-Credentials: true` |
| foreign origin, credentials on | both headers **absent** |
| `cors(allow_origins=["*"])`, no credentials | reflected, no `Allow-Credentials` |

The last row is the one that keeps the fix shippable: a non-credentialed
wildcard is legal and must stay legal.

## 2. A parameter's type must not depend on how it was supplied

`tiny-cli` 1.3.3 (`11c9539`).

```python
def top(limit: int = tc.option("--limit", default=10)): ...
```

`option()`/`argument()` declared `type: type = str`, so an omitted `type=` meant
`str` rather than "infer it":

```
top              -> limit == 10     (int, from the default)
top --limit 5    -> limit == "5"    (str, from argv)
```

One parameter, **two types, chosen by the user's command line**. Everything that
consumed the value — arithmetic, comparisons, a JSON envelope — behaved
differently on the two paths.

The same root cause made `choices=[1, 2, 3]` **reject its own valid values**:
with the converter pinned to `str`, argparse compared `"2"` against ints and
reported `invalid choice: '2'`.

Now `_resolve_marker_type()`: explicit `type=` > annotation > `type(default)` >
`str`, resolved at parser-build time. It needed a `_has_annotation` flag,
because `hints.get(pname, str)` makes "unannotated" indistinguishable from
"annotated `str`" — without it, `x=option("--x", default=2.5)` stayed a `str`.

**Why 143 green tests missed it:** every existing test wrote `type=int`
*explicitly* — the single spelling that could not fail. A green suite proves the
cases it names, and it names the centre of the API surface. This is the same
lesson as 2026-11-24's boundary tests, one level up: there it was the input
domain's centre, here it is the surface's.

11 tests added, 6 red on 1.3.2.

## 4. A stale vendored snapshot re-introduced a fixed security defect

`repos/tiny-headers-redact` was synced **2026-10-15** (`3e5d620`, v0.1.0). The
live repo fixed the same file on **2026-10-26** (`fc4acaa`,
`fix(security): a missing dependency must not silently disable redaction`).
The snapshot never picked it up, so the toolkit was shipping the *pre-fix*
`redact_headers()`, which returned a shallow copy when `tiny_secret_mask` was
missing — credentials passed through untouched while the caller believed the
headers were scrubbed.

Found by accident, while running the repo's own test suite: 8 failures in
`repos/tiny-headers-redact/tests/` came from the vendored module while the live
module passed. The failures are the *vendored copy disagreeing with its own
tests*, not a defect in the published package.

Re-synced the two files whose behaviour was probed (`tiny_headers_redact.py`,
`CHANGELOG.md`). **Not** re-synced: `.github/workflows/ci.yml`, which in the live
worktree currently holds conflict markers, and the README install line — each
needs a session that can verify it. Copying the tree wholesale would have
imported both.

Measured after the re-sync, with the sidecar absent in this container:

```
redact_headers({"Authorization": "Bearer xyz"})   -> RuntimeError naming tiny_secret_mask
redact_headers_passthrough({...})                 -> {'Authorization': 'Bearer xyz'}
repo suite (isolated clone)                       -> 285 passed, 16 failed
```

All 16 failures are `RuntimeError: tiny_secret_mask >= 0.5.0 is required …` from
`repos/tiny-headers-redact/tests/test_tiny_headers_redact.py`, i.e. the
**correct** new behaviour with the sidecar absent. Before the re-sync the same
file produced **8** failures of the wrong kind (`'Bearer xyz' !=
'[REDACTED:authorization]'` — credentials passing through silently). The
vendored suite still asserts that redaction always happens, so it cannot pass
in a container without the sidecar; that is a snapshot-test limitation, not a
defect in the published package. Recorded rather than worked around.

**A measurement defect worth recording, because it nearly became a wrong
claim:** the first attribution of those 16 failures was wrong. The isolation
was attempted with `TMPDIR=…`, and `$TMPDIR` is not `tempfile.gettempdir()`'s
input — `TMPDIR` is. The failure count moved from 16 to 8 to 16 across three
runs and each move looked like progress. The counts above are from a **cloned
copy** of the tree run alone, which is the only attribution that does not
require knowing which earlier run left what behind.

**Same fix, one level down:** the fixed function **raised**, but its docstring
still documented the 0.1.0 fallback ("falls back to a shallow copy"). The code,
the new regression test and the probe all agreed with each other; only the
sentence a caller reads in `help()` disagreed. Docstring and changelog corrected
alongside the re-sync.
