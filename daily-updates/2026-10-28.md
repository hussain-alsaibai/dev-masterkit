## A Repo With Tests And No CI Is Not Tested

Twenty-five tiny-* repositories had a test suite and **no workflow file at
all**. Adding one to each found **8 real defects** - including two libraries
whose central function could never run.

**Every one of those eight had shown a green local test run at some point.**
The reason is a single hole:

```bash
pip install -e .     # the SOURCE TREE goes on sys.path
pytest                # imports the loose .py file next to the test
```

An editable install puts the source directory on `sys.path`, so the test suite
exercises the working tree - fine - but it never proves the **wheel** ships the
module. Five packages passed `pip install -e .` and still published a wheel
containing **zero importable modules**.

### The eight defects

| repo | defect | shape |
|---|---|---|
| `tiny-semantic-cache` | `sum(x * y for y in b)` - `x` is not in that generator, so **every call raised `NameError`** | typo inside a generator |
| `tiny-ai-workflow` | `field(default_factory=None, init=False)` - dataclasses **calls** the factory, so `None()` raised `TypeError` on every step registration | misuse of `default_factory` |
| `tiny-file-watcher` | a scan landing mid-`rename` reported the move as `DELETED + CREATED` | a rename is not atomic |
| `tiny-scheduler` | `shutdown(cancel_futures=...)` is **3.9+**, the package claims `>=3.8` | declared floor not honoured |
| `tiny-bucket-quota` | shipped `py-modules = ["tiny_rate_window"]` - **the wrong module**, copied from a sibling | packaging copy-paste |
| `tiny-llm-router` | `py_modules` instead of `py-modules` - the build failed outright | key typo |
| `tiny-jsonpath` | `package-data` used the empty-string key `""`, which modern setuptools rejects | invalid packaging table |
| `tiny-diff`, `tiny-eval` | two test files with the **same basename**, so pytest refused to collect the second | duplicate basename |

And a packaging class of its own: `tiny-semantic-cache`, `tiny-ai-workflow`,
`tiny-event-bus` and `tiny-task` all shipped wheels with **no importable
module**, because

```toml
[tool.setuptools.packages.find]
include = ["tiny_semantic_cache*"]
```

finds nothing - **a single top-level module is not a package**.

All 25 are green on GitHub now, and every count in this file was measured by
run against the upstream clones.

### A Collection Error Is Not a Test Failure

`snapdb`'s PEP 669 profiler bug produced **11 collection errors**. That reads
like "11 tests failed" but means **nothing ran at all** - the module could not
be imported. The whole suite was unrunnable on two of the five Python versions
in CI, and the badge said nothing about the code.

### A Flaky Test Can Hide A Real Race

`tiny-file-watcher`'s rename test failed **3 of 6** CI matrix jobs and passed
locally most of the time. The first instinct is to lengthen the sleep. **That
is not the bug.** `os.rename` is not atomic: between the two halves the old
path is gone and the new path does not exist yet, and the detector compared
inodes between *consecutive* snapshots, so the pairing was lost permanently.

The fix keeps an `inode -> last-seen-path` map. Verified with a **400-trial**
harness: 0 misses, where the old code missed 2-4 per 60. The *test* fix was
separate and also necessary - a fixed `sleep(0.3)` against a background polling
thread became a condition wait, halving the suite time (4.1s -> 2.1s).

> **Reproduce the race before you fix the test.**

## Five PyPI Names In Our Stack Belong To Other People

A sweep of all 62 package names against PyPI found **5 genuine collisions**:

| our package | PyPI name is owned by | their version | their project |
|---|---|---|---|
| `tiny-router` | nekonoshiri | 0.0.8 | a different HTTP router |
| `tiny-cli` | TinyBio LLC | 0.1.0 | a genomic tooling CLI |
| `tiny-eval` | - | 0.5.0 | "A tiny evaluation framework for language models" |
| `tiny-memo` | meng | 1.1.6 | a memo/note-taking application |
| `tiny-diff` | - | 0.1.0 | "Hackable implementation of diffusion models" |

**Two of those five were in the in-scope READMEs**, and the install line read
`pip install tiny-router` and `pip install tiny-cli`. **Both commands
succeed.** They install a different developer's package. A user following the
README got someone else's code with no error at all.

That is the worst failure shape: silent, and it looks like success. The three
others carried PyPI version badges pointing at the foreign package, so the
badge rendered a version number that was not this project's.

Fixed in 15 repos: install lines now use the GitHub URL, broken badges point
at the GitHub install, and the two collision cases say **plainly why** the PyPI
name cannot be used so a future reader does not "fix" it back.

**Still blocked:** publishing is impossible - no `~/.pypirc`, no
`TWINE_PASSWORD`, no keyring entry. `pysnapdb` is already ours at v0.14.0
against a v0.18.0 repo, so there is an upgrade path for snapdb. The other 57
names are free. The 5 collision names can never be published under their
current names - that needs a rename decision, not a token.

## Never Compare Partial Calendar Months

The first Q4 trends report compared calendar-month download totals. The data
ended on the 25th, so the final month had **25 of 31 days** and every package
looked like it was collapsing.

| package | naive calendar-month | corrected (30d vs 30d) |
|---|---|---|
| `fastapi` | -29.9% | **+28.4%** |
| `langchain` | -45.8% | **-4.4%** |

The corrected method has now been used for two consecutive reports. The
2026-10-28 report covers **160 packages** (was 100 on 10-26), every figure is
re-derived by a script from the raw table, and the raw table ships next to the
report so the arithmetic is checkable.

The corrected comparison also **flipped the conclusion**: agent frameworks did
not consolidate, they **fractured**. `marvin` +80.1%, `agno` +29.8%, `letta`
+29.6%, `langchain-anthropic` +29.3%, while `langchain` itself is **-3.4%** and
`llama-index` **-14.9%**.

> **Trailing 30 days against the previous 30 days. It is partial-month safe,
> and it is the only comparison that survives being written on any day other
> than the 1st.**

## A Slot Budget Is Not A Slice Budget

The bounty scanner collects contributor tasks and cash bounties, then picks a
fixed number of candidates to **score**. The pick was a positional slice - the
first N of the collected list.

On the live sweep the first 100 collected tasks came from only **39 repos**:
`k08200/klorn` alone held **14**, `tonianev/eonmark` **13**,
`exceev-consulting/server-prep` **11**. And `pipeshub-ai/pipeshub-ai` - the
3.8k-star repo the contributor-task path exists for - sat at positions **200 and
238** and was cut before it was ever scored.

Scoring is **per-repo work**: 250 candidates from 39 repos is 39 repos' worth
of metadata fetches and scam detection. Spending that budget on 14 issues
from one 8-star repo buys nothing. **Diversity by repo is the cheaper way to
spend the same budget.**

The fix is a round-robin across repos (`spreadAcrossRepos()`): every repo's
**first** task is taken before any repo's second. The count stays exact, it
stays deterministic, and the flood is still visible - a repo with many tasks
still has its first task scored, it just cannot take the whole window.

## Guide Corrections Found By The Same Sweep

Running every import in every guide against the real sources found four
guides documenting APIs that do not exist:

- **`tiny-eval-guide.md`** documented `eval_expr`, `Sandbox` and
  `interpolate` - **none of the three exists**. The package is an agent
  evaluation framework (`BenchmarkSuite`, `Rubric`, `Criterion`, `AgentRunner`,
  `RegressionTracker`). A reader who copied the snippet got an `ImportError` on
  the first line. The guide is rewritten against the real API, and the
  quick-start snippet was executed before being published.
- **`fast-cache-guide.md`** said `from fast_cache import cache` and
  `from fast_cache import SingleFlightCache`. **Neither import works** -
  verified by importing the module. `fast_cache.__all__` is `Cache`,
  `CacheAsync`, `CacheStats`, `DiskSpillover`, `CacheMetricsListener`,
  `cache_method`; `SingleFlightCache` lives in the `fast_cache_v072` sidecar.
  The guide also claimed `Cache(default_ttl=...)` and `get_or_call`; the
  constructor is `Cache(maxsize, ttl, maxmemory, evict_callback, thread_safe)`
  and the method is `get_or_set`.
- **`tiny-store-guide.md`** imported `LRUCache` from `fast_cache`. **There is
  no `LRUCache` in `fast_cache`** - absent from `dir(fast_cache)`.
- **`tiny-hll-guide.md`** and **`tiny-cli-progress-guide.md`** said "repo does
  not exist upstream yet". Both returned **404** on 2026-10-23 and return
  **200** now (last push 2026-10-26). The stale note is corrected.
