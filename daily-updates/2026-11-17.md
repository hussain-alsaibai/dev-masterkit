## 1. `tiny-cli` 1.3.2 — the marker was resolved by the wrong name

The shortest reproducer is the whole bug:

```python
@cli.command()
def show(user_id: str = tc.option("--user", default="1")):
    return {"id": user_id}
```

```console
$ myapp show --user 9 --json
{"result": {"id": {"_kind": "option", "flags": ["--user"], "default": "1", ...}}}
```

`tc.option("--user")` is a **default-value marker**. The builder handed the flags to
argparse, which derives `dest` from the first long flag (`--user` → `user`). The
dispatcher then looked the parameter up by **its name**, `user_id`. `hasattr` was `False`,
so the parameter was never bound.

| author wrote | command received |
|---|---|
| `--user 9` supplied | the marker default `"1"` |
| flag omitted | the raw marker **dict** |

The second row is the one that reaches production, because a default is the common case.
In JSON mode the dict was serialised straight into `result`; in text mode it was
interpolated into a string nobody compared.

**Why 57 tests missed it:** every existing use used a matching name
(`times: int = tc.option("--times", ...)`), the single case where argparse's derived
`dest` is already correct.

**Fix:** `dest=pname` on both the `store_true` and typed forms. Flag name and parameter
name are now free to differ — which is the reason to have both.

**Proof:** new `test_v131_option_dest.py`, 10 tests, **5 of which fail on the unfixed
module**. Suite **143 passed**, CI `44089048407` green on 3.9–3.13.

### Two more bugs found while writing the corrected docs

1. **An option with no default was optional.** `tc.option("--text")` carries
   `default=Ellipsis`; the builder dropped it, and argparse reads *no default* as
   *optional*. Omitting the flag ran the command with the descriptor dict as the value.
   Author wrote no `default=` → now `required=True`, verified by exit code 2.
2. **A parse error corrupted the JSON envelope.** argparse writes its usage line to
   stdout on some error paths; JSON mode owns stdout, so `jq` failed on the usage line
   while the exit code came from `jq`. stdout is now redirected during the parse and the
   usage line is re-emitted **inside** the envelope's `error` field — relocated, not
   dropped.

## 2. `MotionClone` #44 / PR #65 — the red phase proved nothing

Preview rendering capped the **width** instead of the longest edge, so portrait imports
(`prepare()` allows 1080×1920) rendered at nearly full resolution — `960 / 720 > 1`, so a
720×1280 source got no downscale at all.

The first draft of the regression test used `tracks=[]` and **failed**, which reads as a
successful red phase. It failed at **construction** (`pydantic too_short`), never reaching
the assertion. The fix could have been anything and the test would have gone green.

Corrected fixture → the unfixed code fails on `1280 == 960`, the assertion the bug lives
in.

| source | before | after |

## 5. Corrected — the CLAW revert/return claim

A claim copied forward through four documents said `balanceOf` on the dead wallet
**reverts** and used that as proof of zero burns. Run against the vnet RPC, it **returns
0**. The reverts are real but belong to the **superseded** contract's tax getters.

| check | current contract | superseded |
|---|---|---|
| code size | 4541 bytes | 3170 bytes |
| `burnBps` / `rewardBps` / `totalTaxBps` | 200 / 100 / 300 | REVERT |
| `balanceOf(dEaD)` | **0 (returns)** | 10,000,000 |

The conclusion held; the mechanism did not. Corrected in
`prompts/a-metric-from-random-is-not-a-metric.md` and the 11-15 addendum.

**The prompt's rule survived the correction and is the reason it is kept:** a revert on a
zero-balance address is data, not an error — and a claim carried forward from an earlier
verification is a hypothesis, not a fact.
