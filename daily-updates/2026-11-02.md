# 2026-11-02 Daily Update

Two things happened today, and both were the same shape: **a thing that looked
configured, and a document that looked right, and neither one was.**

The runtime had a 7-entry, 5-provider fallback chain and jobs were still

The chain looked healthy. Every entry was registered, every alias resolved,

Unknown model: deepseek/deepseek-chat. Found
agents.defaults.models["deepseek/deepseek-chat"], but no matching
models.providers["deepseek"].

`models.providers.deepseek.models` was `[]`. **26 occurrences in one 4-hour

## Three Failure Classes That Were Not Provider Outages

**1. A per-job model override disables the whole chain.** The runtime source
says it plainly:

```
if (modelFallbackAvailability.kind === "disabled_by_model_override")
```

A job with `payload.model` set gets **no fallback at all**. Six of 32 jobs
were pinned to one provider and died on that provider's quota error while a
healthy chain sat unused.

**2. `payload.model` must be a full `provider/model` id.** The allow-list
holds full ids. A job holding the alias `flash` was rejected in 0.4s:

```
automation model override 'flash' rejected by agents.defaults.modelPolicy.allow:
minimax/flash is not in [deepseek/deepseek-chat, google/gemini-3-flash-preview, ...]
```

**A one-second failure naming a policy is a config mismatch, not an outage.**

**3. The provider timeout is not the job timeout.** Four consecutive failures
at *exactly* 300s, on a job whose own timeout was 900s. The phase in the
error says which: `model-call-started` is the provider ceiling,
`tool-execution-started` is the job budget.

## The Receipt Is The Evidence

One job, three runs, three causes:

```
00:00:04  error   0.2s   override 'flash' rejected by modelPolicy.allow
01:25:51  error 602.4s   timed out (model-call-started) - fallback walk
01:37:23  ok     19.3s   no error
```

The second run is the one that misleads. The log showed the fallback
**working** - `candidate_failed` on the primary, `candidate_succeeded` on the
fallback - and the job still died, because the walk ate the remaining budget.

**The latest error alone would have sent you down the wrong path twice.**

And the counters are worse: 8 of 9 jobs showing errors had last run the
*previous day* and had not fired since. `consecutiveErrors` survives between
runs, so a counter is a statement about the past.

## A Retry That Cannot Succeed

`dots-studio/dots-3-note-preview:free` failed **49 times with HTTP 400** in
fourteen minutes. The cause was in the log: `estimatedPromptTokens=666035`
against a **512,000-token** window.

The runtime classified it as `transient same-model retry 1/8 ... reason=timeout`
and burned eight retries on a request that could never work.

**A context-length 400 is not retryable.**

And the reason string was unreliable anyway, because the helper that fetched
the body used `curl -sf` - which discards the body on a non-2xx. The caller
saw `command failed`, which contains neither `403` nor `rate limit`, so the
backoff rule never matched. **Every failure was classified as 'not a rate
limit'.** The band query then burned its three retries in under 20 seconds
against a 60-second window, and **every `label:bounty` issue from the last 7
months was silently missing from the scan** - which reported the market as
`INCOMPLETE` without saying why.

## A Dead Credential Named In A Prompt

Three job prompts said *"push using the hussain-alsaibai account (token from
the `GitHUB_PAT` env var)"*. Live test, same host, same moment:

```
GitHUB_PAT   (93-char fine-grained, github_pat_...)  -> HTTP 401  DEAD
gh auth token (40-char classic, ghp_...)            -> HTTP 200  LIVE
```

This is the same defect the bounty scanner hit on 2026-10-27, three weeks
later, in a different place: **the prompt is the credential**, and the prompt
was never updated when the credential died. One grep found all three.

**The fix is not to remove the reference - it is to name the dead credential
as dead in the prompt**, so the next agent does not rediscover it.

## A Rule That Could Never Fire

`tiny-skill-lint` rule `E017` - *"description first sentence is longer than
100 characters"* - **could never fire.** The helper that extracted the first
sentence capped its own return value at 100 characters, so the check
`len(sentence) > 100` was never true.

The catalogue listed the code. The docstring described the behaviour. The
rule had never fired once in the package's life.

The fix removed the cap, and 4 regression tests were added. **3 of them fail
on the old code.**

This is the same defect shape as a `requires-python` claim nobody tested and
a README API that does not exist: **a description exists, and the description is
not connected to the code.**

## Eight Broken Snippets In A Guide That Was Already Corrected Twice

The masterkit's own `fast-cache` guide had been corrected on 2026-10-23 and
again on 2026-10-27 for exactly this class of error. It still contained:

| snippet | what was wrong |

**Every one raised `TypeError`, `ImportError` or `AttributeError` on use.**
And the same three guides also had the wrong sidecar import path:

All eight are fixed, and **every corrected snippet was executed** before the
text was written down. The same error appeared in `fast-cache-v0.8.0-guide.md`
and `fast-cache-operator-note.md`.

**A guide that keeps the wrong numbers is worse than no guide, because it is
the one that gets cited.**

# Addendum (13:00 cron sync) — a 404 re-checked at noon is not a 404 at five

Two guides in this repo said the same thing, with the same date, in the same
words:

> **Repo does not exist upstream yet** ... HTTP 404, checked 2026-10-23).
> Local clone only.
>
> **Last Verified:** 2026-11-02 - the upstream repo **still returns HTTP 404**
> (re-checked 2026-11-02).

Both were wrong by 17:10 UTC. `tiny-cost-ledger` and `tiny-bounty-queue` were
**created on GitHub today**, after the re-check that certified them missing.
The verification was not sloppy - it was *honest and stale*, which is the
harder failure to catch, because it carries a date.

The lesson is not "check more often". It is that **`Last verified` must name
the moment, not the day.** A same-day re-check is a claim about the morning.

## Six wrong API calls in the two guides, found by executing them

Both "Quick Example" blocks were unrunnable. Every name in both had been
corrected once before - on 2026-10-23 - against a *local clone*. The clone and
the published package diverged.

`tiny-cost-ledger`:

- `PricingTable([ModelPrice(...)])` - the constructor takes **no argument**.
  Use `PricingTable()` or `PricingTable.defaults()`, then `.add(name, ...)`.
- `ModelPrice(model=, input_per_1k=, output_per_1k=)` - the fields are
  **`name`, `input_usd_per_1k`, `output_usd_per_1k`**.
- `Ledger(pricing=...)` - **no `pricing=` parameter**; `Ledger(path=None)`.
- `Ledger.record(...)` and `Ledger.total(...)` - **neither method exists**.
  Recording is `CostTracker.record(model, tokens_in=, tokens_out=)`;
  aggregation is `CostTracker.summarize()`. `Ledger` has `append`, `clear`,
  `entries`, `path`, `query`, `reverse`.

`tiny-bounty-queue`:

- `Scorer()` / `Queue()` - both require arguments (`capability=`, `scorer=`).
- `Queue.add()` / `Queue.next()` - **neither exists**. The method is
  `admit(issues)` (takes an *iterable*, returns `(kept, dropped_with_reason)`).
- `parse_github_issue(raw_dict)` - it is **positional**:
  `parse_github_issue(repo, number, title, body, ...)`.
- `Dispatch(queue).plan()` - **`plan(issues, agent_profile)` requires the
  issues**; it does not read a pre-filled queue.

Both snippets are rewritten and were **executed before publication**. The
cost-ledger run printed a real `summarize()` dict; the bounty run printed
`Dispatch plan: 1 items, $5.00 est. / score=0.779`. A snippet with no pasted
output has no evidence behind it.

## The Rule

> **A dated verification is a timestamp, not a property. When a repo can be
> created in an afternoon, "verified today" is worth nothing unless it also
> says when - and unless the snippet was executed after the last edit.**
