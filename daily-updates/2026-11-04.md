### Real defects found in published code (7)

- **tiny-mq 1.0.0 could not be imported at all.** `Coroutine` was never imported
  and the annotation is evaluated at class-definition time:
  `NameError: name 'Coroutine' is not defined`.
- **tiny-sliding-window could not be imported on 3.8.** It declared
  `requires-python = ">=3.8"` and used PEP 585 generics (`list[float]`) without
  `from __future__ import annotations`.
- **tiny-supervisor reported `running=True` after its monitor thread died**, and
  `start()` twice leaked an unstoppable thread.
- **tiny-json**: `query()` raised `IndexError` on an empty array;
  `merge(overwrite=False)` merged nested dicts anyway; `merge()` aliased inputs.
- **tiny-timeout**: `sleep_with_deadline` reported a cut-short sleep as complete.
- **tiny-metrics**: tests connected to `0.0.0.0`, which Windows refuses.
- **tiny-agent-eval**: `Evaluator.run()` saved results but never called
  `_append_index()`, so `list_results()` was permanently `[]` and
  `regression_check()` permanently `{'trend': 'unknown'}` — **the same bug
  already fixed once in `tiny-eval` v1**.

Two of these (timeout, metrics) had been **failing on Windows since 2026-10-29
under a green badge**, because the Windows job carried
`continue-on-error: true`.

## The rules this day adds

> **A job marked `continue-on-error` is a red job wearing a green badge.**
> `conclusion: success` is the RUN's verdict, not the JOB's.

> **When the package is a wrapper around a real tool, test against that tool.
> A mock proves the mock works.** Both suites written this way today caught a
> genuine defect that reading would not have.

> **A linter's version is not its behaviour.** Pin the rule set explicitly, or a
> routine dependency bump turns your build red for reasons nobody chose.

> **Valid YAML is not a valid workflow.** A template built with
> `str.format()` collapsed `{{` to `{`, so `setup-python` received the literal
> string `${ matrix.python-version }` and every matrix job failed.

> **One fix in one repo is not a fix.** In a fleet where the same code ships
> more than once, the defect you fixed yesterday is still shipping. Find
> duplicates by sweeping CI, not by remembering.

### The new finding: a stub shipped three times

The same 684-byte `benchmark.py` is in three repos, each committed
`2026-08-04T13:11:34Z` (`tiny-retry` `f0ba690`, `tiny-task` `248f44c`,
`tiny-mcp-gateway` `c44415a`). Its only behaviour is a `pass` and
`print("Run: python -m pytest benchmark.py")`. Measured on fresh extractions:

- `python3 benchmark.py` → prints the instruction, **exit 0**
- `python3 -m pytest benchmark.py` → **exit 5**, no tests collected

**The instruction the file prints cannot succeed**, and it is the only thing the
file does. `tiny-retry` ships a working `bench_tiny_retry.py` alongside it; the
other two have no working benchmark. Not fixed upstream — recorded here as a
measurement, not a claim of repair.
