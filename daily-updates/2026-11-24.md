## 1. A unit chosen before rounding contradicts its own number

`tiny-log` 0.8.3 (`04c74a1`).

```
bytes_human(1023.9999)      "1024.0 B"    <- 1024 bytes' digits, byte label
bytes_human(1048575.99)     "1024.0 KB"
```

The unit was picked before the value was rounded, so anything within one
rounding step of a base boundary printed a number equal to the next unit's base
while carrying this unit's label. A caller that strips the suffix and parses the
number — a dashboard reading a telemetry field — gets a **1024x** error.

| input | 0.8.2 | 0.8.3 |
|---|---|---|
| `bytes_human(1023.9999)` | `1024.0 B` | `1 KB` |
| `bytes_human(1048575.99)` | `1024.0 KB` | `1 MB` |
| `bytes_human(1023.6, precision=0)` | `1023 B` | `1 KB` |
| `bytes_human(float("inf"))` | `OverflowError` | `inf B` |

Three sibling defects in the same function, all the same shape — **a guard that
covered one of two symmetric cases**:

- `precision=0` **truncated** via `int(v)` where `f"{v:.0f}"` rounds. An explicit
  precision of zero is still a rounding request.
- `inf` reached `int(value)` unguarded. The NaN guard was there; infinity is the
  other non-finite float. It raised `OverflowError` **from inside a logging
  call** — a field formatter must never raise there.
- `SamplingHandler(rates={logging.DEBUG: 0.0})` stored the key `"10"` and looked
  up `"DEBUG"`, so the rate read back as the `1.0` default and **every** DEBUG
  record was kept. Int levels are now normalised through `logging.getLevelName`.

13 tests, **8 red on 0.8.2**. → `prompts/a-unit-chosen-before-rounding-contradicts-its-number.md`

## 2. `nullable` was the missing half of "optional"

`tiny-validator` 0.7.4 (`348695c`).

The library could say a key may be **absent** (`required=False`) but not that it
may be **present and `null`**. `Field.allow_none` was a read-only class property
that only `Any` overrode; `fields.String(allow_none=True)` raised `TypeError`.
The only spelling a user could reach was

```python
fields.String(required=False, default=None)
```

and that schema **rejected every document**, because the `None` default is
validated as a value *before* the field is allowed to be absent:

```
validate({}) -> [{'path': 'tags', 'message': 'value is null'}]
```

`required` and `nullable` are orthogonal facts; a `None` default now implies
nullable, and `required=False` alone still does **not** allow `None`.

**The mirror defect is the one that matters if you import contracts.**
`from_json_schema` accepted `{"type": ["string", "null"]}` by **stripping
`"null"`** and building a non-nullable field — so a contract imported from
OpenAPI or MCP rejected the nulls it explicitly permitted. `"nullable": true`
raised as unsupported. Both forms import now, and the exporter emits
`"nullable": true` instead of advertising a narrower contract than the validator
enforces.

Probed before the tests, on the fixed tree:

```
nullable=True          {"tags": None} -> []      {}  -> missing required field
nullable=False         {"n": None}    -> value is null
required+nullable      {}             -> missing required field
union import           {"a": None}    -> []
plain import (narrowing guard) {"c": None} -> value is null
```

14 tests, **11 red on 0.7.3**. → `prompts/nullable-is-a-field-fact-not-a-missing-value.md`
