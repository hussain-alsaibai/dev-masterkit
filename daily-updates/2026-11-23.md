## 1. A farm that buys its stars is invisible to every star threshold

`limitlessprojects/Go-Hybrid` sat in the shortlist as an uncontested bounty:

```
stars: 33   forks: 329   watchers: 2   open issues: 862   age: 6 weeks
```

Every farm rule in `scanner.js` keys off `stars < 5` (or `stars < 2`), and none
of them runs above five stars. A farm that **pays** for stars therefore passes
all of them. Go-Hybrid was dropped only because `young_repo` happened to fire —
a gate catching it for a reason that did not describe its signature, which the
next wave can evade by waiting six weeks.

The fix is Rule 1b: a **ratio**, not a bigger constant.

```js
const FORK_TO_STAR_RATIO = 3;
for (const [key, flags] of repoFlags) {
  if (flags.some(f => f === 'unmeasured_stars')) continue;
  const x = scored.find(s => String(s.repo || '') === key);
  if (!x) continue;
  const stars = typeof x.stars === 'number' ? x.stars : 0;
  const forks = typeof x.forks_count === 'number' ? x.forks_count : 0;
  if (stars < 4 || forks < 4) continue;   // below 4 the low-stars rules own it
  if (forks >= stars * FORK_TO_STAR_RATIO) flags.push('fork_heavy');
}
```

`fork_heavy` joins `inorganic_forks` and `stats_unverified` as a farm verdict.
`unmeasured_stars` short-circuits the rule, because a repo whose stars could not
be read must not be judged by a rule that divides by them — the same class of
error as the 2026-10-24 quota-death bug.

**Proven in both directions.** The test asserts the rule fires on Go-Hybrid and
does not fire on crewAI (61,153 stars / 9,237 forks), a 6-star repo with 4
forks, or a 1,000-star repo with 1,200 forks; and that the flag is named
`fork_heavy` and not `low_stars`, so the reason stays a readable sentence about
the entity. **19/19** checks green; **1 fails** against the pre-fix scanner (the
"implements the ratio, not a fork count" check).

## 2. `market_complete` meant "no error", not "read"

Two scans of the same query, twenty minutes apart:

```
06:09Z:  10,209 issues
07:12Z:   8,838 issues
```

A market cannot shrink by 1,371 in twenty minutes. The per-source diff located
it in one command:

```
"How to verify"            1686 -> 1209
"help wanted + verify"     1003 ->  109
"Contributor task"         1231 -> 1231
```

`collectBand()` paginated a band and, on a failed page, did `break` — dropping
every remaining page of that band while the band still counted **complete**. The
run had been rate-limited twice (403 secondary limit), so it truthfully raised
no error, and the report said `incomplete_bands: []`, `market_complete: true`.
A truncated page is not a shorter market.

The same defect sat in every single-page sweep: `label:opire` matches **74**
open issues and the sweep read one `per_page=50` page and printed "Opire: 50
issues" as the market. It had been under-reporting that source by 32% for weeks.

```js
// a lost page is now a recorded fact
if (!p || !p.items || !p.items.length) {
  INCOMPLETE_BANDS.push((expr || '(whole query)') + ' page ' + page);
  process.stderr.write('  [CAP] PAGE LOST (page ' + page + ' of ' + pages + '): ' +
    (expr || '(whole query)') + ' - those issues are NOT in this scan\n');
  break;
}
```

plus `searchAllPages(baseQ, label, perPage)` for the opire and `$XX` sweeps:
paginate to `total_count`, pace between pages, mark a lost page incomplete, cap
at 50 pages. `INCOMPLETE_BANDS` non-empty → `market_complete: false` → the
report prints a lower-bound warning instead of a count.

`test-pagination-completeness.js`: **10/10** green, **6 of 10 fail** against the
pre-fix source. Verified live on an unthrottled run: Opire **50 → 74**, exactly
the `total_count` from an independent `gh api` call; "How to verify"
**1209 → 1685**; "help wanted + verify" **109 → 1003**.

## 3. A zero-pick day needs a receipt

Two fields made the zero unreadable:

- `scored_count` counts **post-gate survivors**. It read `0`, and the report
  rendered *"0 reached a score"* — a claim that nothing was ever scored, when
  five candidates had been scored and killed by a later gate. The number was
  true and the sentence false.
- `rejected` is stored as `slice(0, 10)`. **A capped report array is not an
  audit trail**: the two farm rejects that day's gate actually produced were
  absent from the file entirely.

Now:

```js
rejected: rejected.slice(0, 10),   // display convenience
rejected_all: rejected,            // audit trail
gate_counts: {
  scored, shortlisted, rejected_contested, rejected_stale,
  rejected_sponsor, survived_gates,
},
```

and the rendered line reads: *"6,685 issue(s) carried a readable dollar amount;
5 were scored, 5 reached the competition shortlist, 2 survived. Shortlist
deaths: 1 contested, 2 stale."* That is a **success report** with a falsifiable
receipt, and it distinguishes "the gates killed everything" from "the pipeline
never ran".

## 4. The diagnostic worth reusing

**Two runs of the same query with different totals is a bug report, not
noise.** The instinct was to trust the newer number. Comparing three things
located it: the total drop (a claim that cannot be true), the per-source split
(which bands lost pages), and `per_page=1` + `total_count` as ground truth. No
amount of re-reading the code replaced those three numbers.

**And a zero-pick day is a claim about the gates.** One
`gh api repos/limitlessprojects/Go-Hybrid` turned three consecutive zero days
into two real defects; three more scan reruns would not have.
