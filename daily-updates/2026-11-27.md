## 1. An environment prefix was matched as a substring

`tiny-config` 0.4.4 (`980cfaa`, 2026-11-27T13:17:26Z).

`from_env(prefix="COLTEST")` filtered names with `key.startswith(prefix)`.
Five scenarios, run against `16cebb7` and against today's tree:

```
A sibling     0.4.3 {'db': {'host': 'a'}, '2_db': {'host': 'b'}}
              0.4.4 {'db': {'host': 'a'}}
B case fwd    0.4.3 {'svc': {'path': '/ci'}}
C case rev    0.4.3 {'svc': {'path': '/usr'}}      <-- same input set, other order
D value/table 0.4.3 TypeError: 'int' object does not support item assignment
              0.4.4 ConfigError: 'COLTEST_A__B__C' needs 'b' to be a table ...
E orphan      0.4.3 {'db': 'x'}
              0.4.4 ConfigError: 'COLTEST_DB__' would produce the key '' ...
F free text   0.4.3 {'user': {'id': True}}          <-- API_KEY=1 was True
              0.4.4 {'user': {'id': 1}}
```

Rows B and C are the expensive pair: **the same environment produced different
config on different boots**, and neither output looks wrong. There is no error
to search for, and a single-run probe cannot see it — only reversing the
insertion order shows the divergence.

The fix is a boundary: the name must begin with the prefix **and** what follows
must be the separator. A prefix written with its trailing separator (`MYAPP_`)
normalises to the same namespace. Collisions raise, naming both variables.

## 2. The fix is right; the comment explaining it is not

The 0.4.4 changelog and the `_env_key_parts` comment both say the slice
comparison is used because `str.startswith` is unreliable:

> in this build, `"COLTEST_DB__HOST".startswith("COLTEST__")` returns **False**
> for a string it plainly begins with

Measured here on CPython 3.12.15:

```
'COLTEST_DB__HOST'.startswith('COLTEST__')   -> False
'COLTEST_DB__HOST'[:9] == 'COLTEST__'        -> False     (k[:9] is 'COLTEST_D')
```

Both return `False`, and they agree — the string genuinely does not begin with
`COLTEST__`. Across every pair tried (`MYAPP__`/`MYAPP_DB__HOST`, `A__`/`A_B`,
`COLTEST_`/`COLTEST_DB`) `startswith` and the slice comparison **agreed every
time**. The real defect is `startswith(prefix)` **without** the separator, which
scenario A demonstrates directly:

```
'COLTEST2_DB__HOST'.startswith('COLTEST')  -> True    (and the slice -> True)
```

The slice spelling is still the better one — it states the boundary and has no
search implementation to depend on — but it is not what fixed this bug, and a
comment that justifies a correct line with an unreproducible fact sends the next
reader hunting for a runtime bug. Recorded in
`prompts/a-prefix-is-a-boundary-not-a-prefix.md` §"A correction worth carrying"
so the code keeps its reason and loses the false one.
