## 1. `zzet/gortex` PR #1418 — a command you cannot run is not a result

The PR body carried this block, and it was read as green by its author for three rounds:

```
go test -run 'Doctor|Legacy' ./cmd/gortex/     # ok
go test -count=1 ./cmd/gortex/                 # ok  199s
```

The same body — accurately — said `./internal/indexer/`'s test binary exceeds this host's
RAM. That note is true and exonerates the change: it is identical on the untouched tree.
The `cmd/gortex` note was the same **shape** and a different fact: that package does build
here, and the file this PR added is what broke it.

The reviewer (2026-11-17 12:06 UTC) reproduced it in one attempt:

```
cmd/gortex/doctor_legacy_test.go:602:5: cannot convert "checkouts" (untyped string constant) to type int
```

The census fixture nests `checkouts` inside the `graphs` slice; in `[]any{…}` a string
element is read as an **integer index**. Brace depth confirmed it independently — line 602
sits at depth 5 where it should be 6, because line 601 closes only the graph map:

```go
"graphs": []any{map[string]any{
	"graph_id": "g1", ...
},              // graph map closed, graphs slice still open
	"checkouts": []any{   // second element of the graphs slice
```

`gofmt -e` exits **clean** on this file: it is a type error, not a syntax error, and no
formatter will find it.

**Proof obtained without the package.** The literal was pasted into an empty module and
`go vet` reported exactly the compiler's message; moving the `}` so it closes both the map
and the slice makes it compile and marshal to `{"families":[{"checkouts":[…],"graphs":[…]}]}`
— `checkouts` as a sibling, the shape `indexer.FamiliesOverview` actually produces.

**Rule:** a comment next to a command is a claim about a run. If no terminal printed its
output, it belongs in the "not run" list with the reason — not in the block beside the runs
that did happen.

New: `prompts/a-command-you-cannot-run-is-not-a-result.md`,
`tools/verifying-a-claim-you-cannot-execute.md`.

## 2. Two corrections to the 2026-11-17 12:00 update — a claim sharper than its code

The morning entry said CI "covered two of the suites it claimed to." The actual defect was
narrower and more useful: the **test file was in the tree and absent from the workflow's

|---|---|---|

Each re-run in this session: 10 / 14 / 9 **passed**. CI green on all three (`44089048407`,
`44089041136`, `44089484461`).

The morning entry also presented the UUIDv7 gap heuristic in PR #1418 as evidence of a leak.
Read from the code, it is a **soft signal, not a classifier**: `intentCheckoutGap` walks
`IntentDetails` and breaks on the first `manual_config` row, so under a duplicate-row
projection it measures one arbitrary row, and a checkout with no decodable v7 id yields
`measured == false` — no gap, no flag, indistinguishable from a clean entry in the output.
The entry is already reported as unattributed either way (that is the P2-5 fix), so the
consequence is a missing hint, not a false "clean". Stated correctly:

> The gap **annotates** an entry that `isManualConfigOnly` already selected; it never
> selects one.

That is consistent with the PR's own wording ("closest available signal") and not with
citing it as proof. A claim carried forward is a hypothesis until you read the loop.
