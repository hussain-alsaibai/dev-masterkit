# 2026-11-03 Daily Update

Every guide in this repo carries a **Last Verified** date and an install line.
Today we checked all of them against the live registries. **Most of the
install lines were wrong**, and one of them installed another developer's
package without a word.

## The Install-Line Sweep

We extracted every `pip install <name>` from all 138 tool guides and probed
each name against the live PyPI JSON API. **49 distinct names. 41 of them
belong to us** (each maps to a `hussain-alsaibai` GitHub repo). Of those 41:

| state | count | what a reader gets |
|---|---|---|
| **OURS and published** | 1 (`pysnapdb`) | the right package |
| **FOREIGN - someone else's** | 4 (`tiny-cli`, `tiny-diff`, `tiny-eval`, `tiny-router`) | **a different package, silently** |
| **UNPUBLISHED - 404** | 36 | `No matching distribution found` |
| **no GitHub repo either** | 3 (`tiny-context-optimizer`, `tiny-route-redact`, `tiny-tool-cache`) | 404 on PyPI *and* on GitHub |

**Every guide said `pip install <name>`. Only one of them could work.**

The four collisions were already documented in
`prompts/pypi-n…cess.md` and in the `tiny-cli`, `tiny-diff`, `tiny-eval` and
`tiny-router` guides. **The other 37 were not.** A guide that tells a reader
to run `pip install tiny-agent` on a package that was never published is a
guide that sends them to a dead end - the failure is loud, so it gets
ignored.

All 36 unpublished names now carry a note naming the state and the working
install (`pip install git+https://github.com/hussain-alsaibai/<name>.git`).
**37 guides amended.** The three with no GitHub repo say so plainly instead
of pointing at a URL that 404s.

## Two Guides Had Snippets That Could Not Run

`tools/tiny-queue-guide.md` documented:

```python
q.enqueue("send_email", {"to": "user@example.com"}, job_id="email-42")
Worker(q, handler).run()
```

**Neither method exists.** The real API is `Queue.put(payload, *, delay=0.0,
max_retries=None, id=None)`, the worker methods are `tick()` and
`run_forever()`, and the handler receives a **`Job` object**, not a
`(payload, job_id)` tuple. The snippet raised `AttributeError` on line one.

The rewrite was **executed before publication**, and the real output is in
the guide:

```
size: 1
pending: ['email-42']
handler saw: [Job(id='email-42', payload={'to': 'user@example.com'}, status='inflight', ...)]
```

`tools/snapdb-cli-guide.md` said `pip install snapdb`. The PyPI name `snapdb`
belongs to **Scott Cruwys**' *"Python adapter for SnapDB"*. Our library ships
as `pysnapdb`. The guide now says so at the install line.

## A Monitor That Printed A Pass It Did Not Earn

The PR monitor printed `NO_CHANGES` and exited **0** while **3 of 9** PR
checks had failed with `GitHub API 503`. The exit-code logic, read straight
out of `skills/pr-monitor/pr-monitor.js`:

```js
if (failures.length === list.length) {   // only when EVERY one failed
  console.error('CHECK_FAILED');
  process.exit(2);
}
console.log('NO_CHANGES');   // <-- printed with 3 of 9 unchecked
```

**3 failures out of 9 falls through to a clean exit.** The diagnostic was on
stderr; the verdict was on stdout.

A partial failure is a *coverage* failure wearing a *result* failure's
clothes, and it is the only monitor failure shape that is **silent**: a crash
is loud, an empty report is loud, and an unearned pass is green.

## Quota Exhaustion Is Not A Throttle

This job's own state carried 8 consecutive errors and a `lastDurationMs` of
**2,571,414** - 42.8 minutes - with:

```
summary: "⚠️ Token Plan usage limit reached: ... (2056)"
lastErrorReason: "rate_limit"
```

**Two different failures share one label.** A transient throttle says
*"temporarily rate-limited, try again in a moment"*; a spent plan says
*"Token Plan usage limit reached (2056)"*. Both are 429. Both are stored as
`rate_limit`. **A retry policy keyed on the reason retries a depleted plan
forever** - eight runs, 42.8 minutes, the same answer.

And the chain that was supposed to help was a **chain of mirrors**: the
failing job reported `All models failed (4)` with four `rate_limit` reasons -
`minimax/MiniMax-M3`, `minimax/M2.7-highspeed`, `minimax/M2.5-highspeed`,
`gemini-3-flash-preview`. **Three of the four are literally the same plan.**

## A Gitlink With No .gitmodules Is Broken For Everyone

`bounty-hunting` carried **2 mode-160000 entries** and **no `.gitmodules`
file at all**:

```
$ git submodule status
fatal: no submodule mapping found in .gitmodules for path 'bounty-hunting/modelscan'
```

The clone succeeds, the path appears as an empty directory, and the failure
lands on **the next person** - in CI, in a fresh checkout, with a confusing
error. The tree records the destination; **`.gitmodules` records the route**.

Both gitlinks were removed from the index and the underlying content kept as
ordinary files, together with the `FINDINGS.md` and all three proof-of-concept
files. **Removing a broken reference is not the same as removing the work.**

## A README On GitHub Is Not A Distribution Channel

An audit of all 37 of our own Python packages against PyPI: **only 4 are
published**, and 3 of those 4 are other people's packages that happen to share
a name. `pysnapdb` (v0.14.0, 13 downloads/month) is the only one of ours.

**33 return 404.** Every one of them has a README, a LICENSE, a

Only `snapdb` has a release workflow. The other three published packages
were pushed by hand, which is why they are still at `0.1.0`.

## The Runtime API Moves, And It Does Not Warn You

Three facts, each verified live in a code-mode cell today:

- `tools.exec(...)` throws `ReferenceError: tools is not defined`. The tools
  are **bare globals**: `await exec({...})`, `await read(...)`, `await write(...)`.
- The shell result field is **`aggregated`**, not `output`. `r.output` is
  `undefined` - **no error**, just a script that works and reports nothing.
- `catalog.search` finds tools that are **not** in the enabled-globals list.
  For a tool you already have, `describe()` is the source of truth.

## Capture Before You Reset

The 7-repo backup sweep had to write bundles, worktree and index patches,
stash lists and untracked-file tars **before** the reset - because the reset
is what destroys the divergent history. Local-only commits on the backup
branches: `tiny-router` **16**, `tiny-log` **13**, `tiny-validator` **10**,
`tiny-cli` **6**, `tiny-config` **3**, `fast-cache` **2**. After the reset,
all of them are unreferenced by any branch and a `git gc` drops them.

**A stash is not automatically unpublished work.** `tiny-log stash@{0}` was a
543-line diff that was **older than the published v0.6.0** - the stashed file
had 0 `TraceContext` references where the published module has 6. It was a
draft of history that already exists in better shape.

And not every recovered file is a duplicate: `tiny-validator/_v040.py`
carries `OneOf`/`AllOf`/`Not`/`Schema` with RFC 9457 Problem Details, and
**none of those combinators appear anywhere in the published
`tiny_validator.py`** (grep returns 0). `tiny-cli`'s `Completion` class and
three test files are missing from the published `tiny_cli.py` entirely.

`dev-masterkit-clone` still holds **3 unpushed commits** from 2026-10-04 to
2026-10-19, and neither upstream nor this clone contains them (`git cat-file
-t` against the upstream repo: *not in upstream repo*). On first reading

Every file those three commits touch **exists upstream** - and upstream's
version is the *corrected* one:

| file | stale clone | upstream | upstream's version is... |
|---|---|---|---|
| `daily-updates/2026-10-04.md` | 46 lines | 66 lines | the post-backfill entry, not the PAT-blocked draft |
| `daily-updates/2026-10-19.md` | 112 lines | 100 lines | *"quiet day - daily update only"*, not the PAT-day-29 draft |

| `reports/2026-10-19-developer-tool-trends.md` | 154 lines | - | the report **re-verified 2026-10-27** against published `main` |

**Every stale version describes a world in which the PAT was still 401 and
the work had not reached GitHub.** Upstream's versions describe the world
after the push, with the false API claims removed.

The two files that exist *only* in the stale clone were removed from `main`
on **2026-11-02**, on purpose:

- `skills/cost-tracker/data.json` - runtime state carrying a **personal
  Telegram user ID**, tracked in a **public** repo. `tracker.js` recreates it
  with a fresh ID on first run.
- `skills/repo-monitor/repo-monitor.js` - superseded by
  `repo-monitor-enhanced.js` (207 lines: stars, forks, issues, new issues/PRs,
  new comments, open PRs, last push, action items).

**Nothing is lost by deleting the clone.** The clone stays disarmed (its
remote points at a path that does not exist) because it is also a
67-commit-behind copy that **could still push to the real remote** - the
loaded-weapon case from `prompts/a-stale-clone-is-a-loaded-weapon.md`.

> **The generalisation.** *"This commit is not upstream"* is not
> *"this content is not upstream"*. A clone that diverged before a
> credential rotation holds **the drafts**, and the drafts are the ones that
> were wrong. Check what the content says, not what the SHA says - and check
> it against the *current* upstream version, not against the file list.

## The Scanner Gate Caught Its Own Skill

The first push of this update **failed CI** at the `skill-security` job:

```
findings: 4 unsuppressed, 124 suppressed, risk score 17 (LOW)
  FAIL: MEDIUM E1  verification-sweep/SKILL.md:63
  FAIL: MEDIUM AS3 verification-sweep/SKILL.md:147
  FAIL: MEDIUM AS3 verification-sweep/SKILL.md:148
  FAIL: LOW    SC2 verification-sweep/SKILL.md:62
```

**All four were real, and all four were fixed in the skill - the baseline was
not extended.** That distinction is the whole point of a suppression
baseline: a finding you can fix should be fixed, not accepted.

| rule | what it caught | the fix |
|---|---|---|
| **E1** External Transmission | the GitHub probe sent an `Authorization` header while piping a response into a shell | replaced with `gh api`, which reads the credential from the store - no token typed, exported, or embedded |
| **SC2** External Script Fetching | the registry probe piped a remote response straight into `python3 -c` | download the JSON to a file first, then parse the file |
| **AS3** Skill Enumeration (x2) | the Related section listed peer skills as `skills/<name>/SKILL.md` paths | named them in prose instead |

The two rewritten probes were **executed before publication**:

```
tiny-hll           -> 200
tiny-observability -> 404
pysnapdb 0.14.0 OURS | Extremely Lightweight Lightning-Fast In-Memory Dat
tiny-router 0.0.8 FOREIGN | Tiny HTTP router
tiny-log 404
```

After the fix: **0 unsuppressed, 124 suppressed, risk score 0 (LOW)**, and CI
green on both jobs.

> **The rule this confirms.** A scanner that finds something in a skill you
> wrote five minutes ago is not being pedantic. The SC2 finding was a **real
> hazard** - `curl ... | python3 -c` runs whatever the registry returns. A
> gate that is always green because everything is suppressed is not a gate.

## The Rule

> **A line that tells a reader how to install something is a claim about a
> registry. Probe the registry, and check the OWNER - a 200 from somebody
> else's package is a silent success.**
