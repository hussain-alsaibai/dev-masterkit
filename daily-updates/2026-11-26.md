## 1. An imported `enum` validated but did not survive the export

`tiny-validator` 0.7.5 (`161f444`).

```python
doc = {"type":"object","properties":{"role":{"type":"string","enum":["admin","user"]}}}
tv.from_json_schema(doc).validate({"role": "superadmin"})
# -> [{'path': 'role', 'message': "value must be one of ['admin', 'user']"}]
```

The library looked **completely correct**. It rejected the bad value. What it
also did, silently, was publish a contract that accepted every string:

```
0.7.4  to_json_schema -> {'role': {'type': 'string'}}
0.7.5  to_json_schema -> {'role': {'type': 'string', 'enum': ['admin','user']}}
       (+ 'additionalProperties': False, now emitted and honoured on import)
```

`from_json_schema` added a **validator** and never a **constraint**; the export
builds from `field.constraints`, not from validator messages. Only the
consumers — OpenAPI documents, MCP tool schemas, generated clients — saw the
wrong artifact. **No validation test can see this**, because a validation test
asks the first question and the defect is in the second.

This is `an-exporter-must-be-checked-by-a-third-party.md` (2026-11-12, `required`
list built from the wrong predicate) recurring in a new field, found by the same
probe: **read the export, do not read the validator's response.**

## 2. `update()` was a whole-record write with patch syntax

`snapdb` 0.18.5 (`8a87963` + `288e97e`).

```
insert({"name":"alice","age":30,"role":"admin"})
update(0, {"age":31})
get(0)   ->  {'age': 31}          name and role erased, no error

after 0.18.5:
update(0, {"age":31})  -> {'name':'alice','age':31,'role':'admin'}
update(99, {...})      -> IndexError: no document at index 99
replace(0, {...})      -> the old whole-record behaviour, correctly named
```

Three separate failures in one function:

1. **The name lied.** `update` means *change what I named*; the implementation
   meant *make this the record*. The dangerous payload is the partial one.
2. **Silence.** Row still existed, edited field correct, everything else gone.
   For a store used as an agent audit trail this is the worst shape: the record
   reads as if those fields never existed.
3. **A write with nowhere to go invented a row.** `update` on a nonexistent
   index wrote a placeholder; the caller believed an existing record changed.

**Why 264 green tests missed it:** every one passed a **complete** record —
`{"name":"Alicia","age":31}` — the single spelling where a rewrite and a patch
are indistinguishable. Same shape as 2026-11-25's `tiny-cli` (every test wrote
`type=int` explicitly) and 2026-11-24's boundary tests. **One test per write API
with the minimum valid payload** is the test that separates them; a complete
payload cannot, at any count.

**Known limitation recorded, not fixed:** a real `0` in an int/float field on a
nullable column reads back as absent, because the empty slot and zero are the
same bytes. Strings and booleans round-trip (`""`, `False`). Fixing it needs a
per-column presence sentinel and a row-width change — schema-level, not a
decode tweak. Documented in snapdb's CHANGELOG under 0.18.5 "Known limitation";
deliberately kept out of the `update()` tests to avoid conflating two failures.

## 3. A version number chosen before fetching was already published

Both releases above required a second attempt, for the same reason.

```
edit version -> 0.7.4
git push  ->  ! [rejected]  (fetch first)      # remote had 0.7.4 two days earlier
git rebase -> CONFLICT (content): CHANGELOG.md # both sides added the same heading
```

A local clone's top CHANGELOG entry describes **local head**, not what is
published, and a repo several commits behind shows nothing wrong: tests pass, the
version guard passes, the changelog reads correctly.

And `snapdb` carries its version in **three** places — `snapdb/__init__.py`,
`pyproject.toml`, `package.json`. The first bump edited two;
`test_version_consistency` failed on the third, after the commit. The test did
its job; the lesson is that *"bump the version" is a multi-file edit whose file
list is read from the repo, not recalled.*

would be the "re-run is not a re-run" mistake. Recorded so the next session does
not read red as a regression from this commit.
