## 1. Fifteen repos told an agent to run an install that 404s

`llms.txt` in fifteen of our own repos said `pip install <own-name>`. None of
those names are on PyPI. An agent copies the line, gets
`No matching distribution found`, and has no way to distinguish that from "the
library is broken".

**The README of every one of them was correct** — `pip install
git+https://...`. The repo knew the truth; the file written for the agent
reader was wrong, and the agent reader is the one that cannot notice.

### The guard that was green the whole time

`tiny-config` and `tiny-validator` both shipped `test_llms_drift.py`. Both
passed, every day. Read from `origin/main` in this session, it is seven tests:

```
test_version_header_matches_pyproject
test_header_matches_module_and_pyproject
test_python_floor_matches_pyproject
test_documented_api_present          (parametrised)
test_listed_names_are_real           (parametrised)
test_masking_table_matches_reality
test_schema_export_is_valid_and_marker_free
```

The version header, the Python floor, the exported API list, the masking
table. Thousands of words of coverage and **not one assertion on the install
command** — the one line in the file a reader acts on.

**Coverage that is large is not coverage that is placed.**

### The three-way PyPI test

```
curl -s -o /dev/null -w "%{http_code}\n" https://pypi.org/pypi/<name>/json
```

| result | meaning | the line must say |
|---|---|---|
| 404 | unclaimed | the `git+https://` specifier |
| 200, ours | published | the plain name is fine |
| 200, not ours | **squatted** | git URL **plus** an explicit "do NOT run `pip install <name>`" |

Verified in this container today: `tiny-bulkhead` → **404** (free),
`tiny-config` → **404** (free), `tiny-cli` → **200** (squatted, not ours).
`tiny-cli` is the only correct file of the fifteen, and its collision note is
now the template the others follow.

### Two guard drafts that only failed when run

1. **"The name is in `pyproject.toml`"** — passed on all three broken files.
   The declaration is the claim under suspicion: a repo can write
   `name = "tiny-config"` while PyPI hands that name to someone else.
2. **A six-line forward window for the warning note** — reached past
   `- Docs:` and let `tiny-cli` pass by accident, for the wrong reason.
   Worse, moving the note above the install line made the *corrected* files
   fail their own test.

Both were invisible in the diff and immediate against `git show HEAD:llms.txt`.

New: `prompts/a-drift-test-can-measure-the-long-part.md`,
`tools/auditing-an-agent-facing-install-line.md`.

## 2. A stale clone made the shipped fix look unshipped

Checking the fix afterwards from `repos/`, three clones still showed the
original broken line. The obvious reading — "the push never landed" — was
wrong. Asked directly:

```
gh api repos/hussain-alsaibai/tiny-config/contents/llms.txt
  - Install: `pip install git+https://github.com/hussain-alsaibai/tiny-config.git`
    ... `pip install tiny-config` would fail with "no matching distribution".
```

The clone was **3 commits behind** `origin/main`. `git log -1 origin/main`
inside it showed the old tip, because in a stale clone `origin/main` is a
memory, not a query.

This is the mirror of the standing stale-clone rule. There the danger is
pushing *over* newer work; here it is **re-doing work that already shipped** —
a duplicate commit, or a re-application of the same three-line fix, reported as
a fresh fix.

```
git -C repos/<name> fetch -q origin && \
git -C repos/<name> rev-list --count HEAD..origin/main      # 0 == current
```

New: `prompts/a-stale-clone-makes-shipped-work-look-unshipped.md`.

## 7. Late sync (13:00 EST) — the issue was unclaimed and already fixed

Added after the morning sync, from the same day's discovery run.

`marketcalls/openalgo` #1820 looked like a clean pick: `assignee: null`,
`comments: 0`, and no matching open PR. The bug was **real** — verified against
upstream `main`:

```
restx_api/schemas.py:227  offset = fields.Str(required=True)   # no validator
restx_api/schemas.py:262  offset = fields.Str(required=True)   # no validator
restx_api/data_schemas.py:23  validate_option_offset           # correct, uncalled
```

`validate_option_offset` (ATM / ITM1-50 / OTM1-50) exists and is applied in
`data_schemas.py:147`, but is never wired into the two order schemas, so
`offset="BOGUS"` reaches the live order path. A red-then-green test showed 9
failures without the fix, 15 passes with it.

But the slot was not free:

```
issues/1820/timeline   -> cross-referenced #1873
pulls/1873/files       -> restx_api/schemas.py, test/test_order_schema_validation.py
pulls/1873             -> open, 107 additions, last commit 2026-08-25
```

Three field-level readings agreed with each other and all three were measured
on the wrong surface: `assignee` does not list a PR author, a cross-reference is
a timeline event and not a comment, and the PR title used "offsets". **An
unclaimed issue is not an unfixed issue.** No PR was opened.

The discovery note also said "no matching open PR" — corrected here rather than
left to a later session to re-derive.
